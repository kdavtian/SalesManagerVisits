# Risk and technical-debt register

Severity follows [severity-definitions.md](severity-definitions.md). This
register was seeded from a direct audit of `main` at the time the quality
baseline was established (see [README.md](README.md)) — every entry below
is a real, verified gap found while doing that audit and the security-
hardening work that preceded it, not a hypothetical. Add new entries here
as they're found; don't let them live only in a PR description or a
comment thread.

**Status values**: `Open` (not started), `Tracked` (accepted, scheduled or
deliberately deferred with a stated reason), `Mitigated` (reduced but not
eliminated), `Closed` (resolved — keep the row for history, don't delete).

| ID | Area | Severity | Description | Impact if it fires | Recommended action | Status |
|---|---|---|---|---|---|---|
| R-01 | Infrastructure | **High** | Only one environment exists (production, one droplet). No staging. | Every schema migration, dependency bump, and behavior change is validated for the first time against real user data in production. | Stand up a staging environment (second droplet or a lighter split on the same host) that runs the same Docker Compose stack against its own database, seeded/anonymized from production periodically. See [change-management-policy.md](change-management-policy.md) for the concrete plan. | Open |
| R-02 | Infrastructure | **High** | Database backups are a manual `pg_dump` command documented in `deploy/digitalocean.md`, not an automated job. Same for the `uploads_data` volume (photos, POD signatures). | An incident or bad migration between manual backups loses everything since the last one someone remembered to run. | Automate nightly `pg_dump` (retained N days, shipped off-droplet) and a periodic uploads-volume snapshot. Define and test an actual restore procedure, not just a backup command. | Open |
| R-03 | Process/org | **High** | The repo has exactly one collaborator (verified via the GitHub API). Every PR in this project's history was authored and merged by the same account, with no second human reviewer. | Bus factor of one; no independent human catch for a bad change before it merges, beyond CI and AI-assisted review. | Documented honestly in the [ownership matrix](release-and-incident-ownership-matrix.md) rather than hidden. If/when a second person joins, require their review on at least High/Critical-risk changes (auth, payments, migrations). | Tracked |
| R-04 | Process | **High** | Branch protection on `main` (require PR, require the CI check, block force-push) is **documented as policy but not yet technically enforced** — no tool in this session's toolset could set it via API; it needs to be applied by hand in GitHub's UI. | The "every change requires review and CI" completion gate is a convention until this is turned on, not a hard constraint. | Apply the exact settings listed in [change-management-policy.md](change-management-policy.md) → "Enable branch protection (manual step)". | Open |
| R-05 | Reliability | **Medium** | No job runner: overdue-visit reminders, stale-packed-order alerts, ERP-sync monitoring, and the daily summary all run as `setInterval` timers inside the single Express process. State (lockout counters, last-notified dedupe maps) lives only in process memory. | A process restart silently resets in-flight dedupe state (e.g. a locked-out account unlocks early; the daily summary could double-send the same day). None of this scales past one app instance — running two would double-fire every job. | Acceptable for current single-instance scale. If the app is ever horizontally scaled, this needs a real job scheduler or a DB-backed lock/dedupe layer before that happens, not after. | Tracked |
| R-06 | Routing | **Medium** | OSRM's road-network data is a manual, one-time `osrm-extract`/`partition`/`customize` step against a downloaded `.osm.pbf` file — not reproducible by CI or the deploy script. | If the droplet or the `osrm-data` volume is ever rebuilt without re-running that manual step, delivery routing silently falls back to straight-line distance with no alert that it happened. | Script the extract steps (or document a checksum/health check that alerts if OSRM is unexpectedly falling back). Low urgency since the app already degrades gracefully. | Tracked |
| R-07 | Testing | **Medium** | `test/integration/orderLifecycle.test.js` intermittently fails in the full suite (not when run alone) — root cause is a fire-and-forget `notifyUser()` call in an order-notification code path outliving the test's own fixture cleanup in a different file, occasionally throwing an FK-violation `unhandledRejection` after the test has already ended. Observed directly during this baseline's own CI validation. | Intermittent CI red on an otherwise-correct change, undermining trust in the "CI red is real" rule this baseline is trying to establish. | Traced to the actual source: `notifications.js`'s `notifyUser()` called `push.js`'s `sendPush()` without awaiting it, so a later rejection (e.g. a push-delivery DB query hitting a since-deleted row) had no connection to any caller's try/catch, not the order-notification call sites themselves (those already awaited their own work correctly). Fixed by awaiting and catching `sendPush()` inside `notifyUser()`, so it can no longer reject for that reason regardless of whether callers await it. Verified with 4 consecutive clean full-suite runs. | Closed |
| R-08 | Dependencies | **Medium** | `npm audit` reports a moderate advisory (`uuid` via `exceljs`, no non-breaking fix available — `npm audit fix --force` would downgrade `exceljs` to 3.x). CI's `npm audit --audit-level=high` deliberately doesn't gate on this. | Low exploitability in this app's usage (server-side xlsx generation, not attacker-controlled input), but it's a silent gap until reviewed. | Re-check on Dependabot's next `exceljs` bump; ratchet CI's audit level down to `moderate` once this is clear, per the note already left in `ci.yml`. | Tracked |
| R-09 | Secrets | **Medium** | No documented rotation process or schedule for `JWT_SECRET`, `ERP_SYNC_KEY`, or the VAPID key pair. | A leaked secret (e.g. via a compromised droplet or an accidentally-committed `.env`) has no defined recovery procedure — rotating `JWT_SECRET` also invalidates every active session, which needs a communicated plan, not an ad-hoc one during an incident. | Write a short runbook: rotate → what breaks → who to tell → how existing sessions are affected. Do this before it's needed, not during an incident. | Open |
| R-10 | Map/performance | **Low** | Viewport/region payload limiting for the map (improvement-list item 7.4) was scoped server-side only (`customers` GET now accepts a lat/lng bounding box) — the map's own live fetch was deliberately not wired to use it, since doing so touches lastCustomers-dependent features (filters, route planning, nearby search) that couldn't be verified live in this sandbox (tile CDN blocked here). | Map continues to fetch the full customer list on every load; fine at current scale (~200 customers), a real cost only if that count grows an order of magnitude. | Revisit if/when the customer count grows meaningfully; the server-side capability already exists to build on. | Tracked |
| R-11 | Process | **Low** | Dependabot (added this baseline) opens PRs automatically, but nothing yet assigns or reminds anyone to review/merge them. | Dependency PRs silently pile up unreviewed. | Assign Dependabot PRs to the code owner in `.github/CODEOWNERS` (already covers `*`) and revisit at least monthly — see the [ownership matrix](release-and-incident-ownership-matrix.md). First batch (PRs #133–138) was triaged same-day: 4 merged after CI + changelog review (`actions/setup-node`, `express-rate-limit`, `bcryptjs`, `dotenv`), 1 held with a documented blocker (see R-12), 1 (`actions/checkout`) confirmed green on re-run and merged. No recurring process exists yet for the *next* batch. | Mitigated |
| R-12 | Dependencies | **Medium** | Dependabot's `express` 4→5 bump (PR #138) fails `npm ci` outright: `express-async-errors@3.1.1` (used to patch Express 4's lack of native async-error handling, see `server/src/app.js`) peer-depends on `express@^4.16.2` and conflicts with `express@^5.2.1`. Caught by CI on the PR itself, not merged. | None today — the PR was never merged. The upgrade itself is worth doing (Express 5 handles async route-handler errors natively, making `express-async-errors` unnecessary), but needs `express-async-errors` removed and Express 5's other breaking changes (default query-string parser changed from `qs`-style to a simpler one, stricter `res.status()`) checked against actual usage first. | Done: dropped `express-async-errors`, upgraded to `express@5.2.1`. One real breaking change found and fixed — the SPA catch-all route used a bare `app.get("*", ...)`, which Express 5's path-to-regexp no longer accepts (and whose named-wildcard replacement, `/*splat`, wouldn't have matched the root path `/` itself); switched to a raw RegExp (`app.get(/.*/, ...)`), the same approach already used for the CSS route. Audited for `res.status()` with non-literal args, `req.query` reassignment, `res.redirect()`, `app.param()`, and nested/array query-string usage (client only ever builds flat `URLSearchParams`) — none found. Verified async errors (an uncaught Postgres error from an async route handler) still reach the global error handler natively. Full suite + `verify:ui` pass; live-smoke-tested root path, SPA fallback, API 404, and the async-error path against a running server. | Closed |
| R-13 | Infrastructure/Testing | **Critical** | `deploy/deploy.sh --full` ran `docker compose run --rm app npm test` against the **persistent, production `db` service** — the only Postgres in `docker-compose.yml` before this fix, since `app`'s `DATABASE_URL` always pointed at it and `docker compose run` inherits that. There was no isolated test database on the droplet the way CI's own ephemeral `postgres` service provides. Discovered live on 2026-09-17: a `--full` deploy (auto-triggered by the Bonuses migrations landing) ran the real integration suite against production, which both created/deleted real fixture rows (3 test-file failures left 6 orphaned `users` rows behind — cleaned up manually afterward) and, critically, exercised the same order/checkin/payment notification code paths production traffic does, sending real Web Push notifications (`push.js`) to real subscribed devices for fake test orders, at least 3 times across the session (confirmed via `Push delivered to subscription ...` log lines with real subscription/user IDs). Telegram notifications (`telegram.js`, same pattern) were not configured in this production `.env`, so that vector didn't fire this time, but would have under the same conditions. | Any future `--full` deploy (which auto-triggers whenever new migration files are present, not just on request) repeats this: real user-visible confusion from fake push notifications, and a real risk of a fixture colliding with production data (as the failing tests did, against a real `erp_customer_id`). | Two independent fixes shipped together: (1) `docker-compose.yml` gained a `db-test` service under a `profiles: ["test"]` gate (never started by a normal `up`), no named volume (always starts empty); `deploy.sh`'s full-test step now starts it, runs migrations and `npm test` against it with `DATABASE_URL`/`NODE_ENV` overridden via `docker compose run -e`, and tears it down in a trap so a test failure still cleans up. (2) Defense in depth: `push.js`/`telegram.js` now also gate `enabled` on `process.env.NODE_ENV !== "test"`, independent of whether real credentials are configured, so even a future misconfigured test run can't send a real notification. See `docs/incident-response.md`'s postmortem log for the full writeup. | Closed |
