# Business / domain rules (decisions the owner has made)

## Company
KAD Motors (Armenia), distributes Castrol (also Lotos, Orlen, Royal) lubricants. Field sales managers visit workshops/oil-change points; office staff (director, CEO, operations director, accountant, warehouse, delivery) use the same app. Currency AMD; liters matter as much as money.

## Customers
- Category (`customers.category`, stored as Armenian text, label via `categoryLabel`): oil change point (Յուղման կետ), workshop, shop, garage, other.
- Tier (`customer_tier`): `potential` (no ERP link yet, default for new), `bronze` (auto when an ERP customer id is entered while tier is potential; silver/gold are never auto-downgraded), `silver`, `gold`, `competitor`. Colours: gold/silver/bronze must look like gold/silver/bronze. Customer-list icon: category glyph with outline + glyph in tier colour, white/none inner fill. Map pins: ALL our customers (bronze/silver/gold) are one green (clearly distinguishable from red); potential stay red; tier is not shown on the map.
- ERP link: `erp_customer_id` (Excel "Customer ID"). Only linked customers show debt/orders/last payment. Prevent duplicate ERP ids.
- Sales channel (a.k.a. "direction"; codes like SM YVN, SM DAVTASHEN, SM SHIRAK, SM CAS, SM B2B, CVO, PCO, OEM, KF, CAS, retail) and assigned manager come automatically from region/subregion via `route_distribution` when creating a customer; CVO/PCO/OEM etc. the user sets manually. Channels KF/CAS/CVO/PCO/OEM never become "overdue" (not visited in the field). Region/subregion are auto-detected from the pin (Armenian names stored; display in current UI language). New-customer default name = `<Subregion> / Yuxman ket` in English transliteration (e.g. `Armavir / Yuxman ket`), editable.
- Sales managers see ONLY customers assigned to them, plus ERP data only for those; management sees all. Customer edits by managers go through edit requests (admin sees a requests list + notifications).
- Visit planning model (v1.252.0): three sources decide when a customer is visited -- (1) one-off day plans `visit_plans` (approval flow), (2) recurring weekday rules `visit_plan_rules` set on Route Plans (picked `customer_ids` and/or region `areas`; an explicit plan row for that rep+date overrides the rule), (3) cadence `customers.visit_frequency_days` (default 7 since migration 088 -- every existing customer was reset to 7, old values kept in `customer_visit_frequency_backup_088`; new-customer default via `app_settings.default_visit_frequency_days`; last check-in + N days = due-by; drives Overdue). `GET /api/customers/:id/visit-schedule` joins them (next 28 days of planned dates tagged `plan`/`rule`, plus cadence due-by/overdue); sales managers only see their own plans. **Single planned date (v1.253.0, `server/src/utils/visitDue.js`)**: planned = first route weekday on/after last visit + N days (a route day inside the N days is skipped: visited Tue 22 Sep, route Fri, N=7 -> Fri 2 Oct); no route rule -> last visit + N. Customer stays Visited until that date passes; `overdue` (list, `GET /:id`, visit-schedule) = today > planned date (+`overdue_days`). Map popup/customer card show 3 rows: debt, last visit, then `Planned <date>` / `Planned today` (a Plan Day plan includes today) / red `Visit overdue N days` chip + missed date. Map remembers last pan/zoom in sessionStorage `fv_map_view` (plain browsing only). The SQL `visited=overdue` list filter and dashboard/reminders are still pure cadence. Old `planned-visits` endpoint (explicit plans only) is what made the map say 'No planned visits' for rule-based plans.
- Products-at-the-shop (v1.251.0): `GET /api/customers/brand-summary` (sales managers: own customers only; `?customer_id=`) aggregates check-in `brand_status` ({castrol|lotos|royal|competitors:[...]}): `current` = per brand group the latest visit that recorded that group (a visit that skips a group leaves it unchanged), `ever` = every recorded value + latest date. Customer card shows `current` as chips (section between Next visit and Visit history; action buttons bar now sits ABOVE the Next visit card). Customers search matches `ever` labels (e.g. `fake castrol`, `usa castrol`, `mobil`; EN aliases + current-language labels) and a tri-state filter `Products on the shelf` (any visit ever, OR semantics); cards show why they matched (`Fake Castrol · Oct 6`). Client: `brandChips.js`.
- Customers tab filters (all tri-state accordion sheets): assignment (direction -> manager), region -> subregion, customer type -> tier (replaced the old Direction filter in v1.244.0). Status chips: all/visited/overdue/not visited.
- Search matches name, address, ERP id, phones, social profiles, and more.

## Pricing (v1.244.0)
Products carry `bronze_price_amd` (+`unit_price_amd` mirror), `silver_price_amd`, `gold_price_amd`, `retail_price_amd`, `landing_cost_amd`, net cost, `hc_code` (accounting product code), `family`, `brand`, `unit`, `stock_qty`.
Order line price is resolved on the SERVER from the customer's tier (`server/src/tierPricing.js`): bronze/potential/competitor -> bronze (if empty or 0 -> silver); silver -> silver, else bronze; gold -> gold, else silver, else bronze. 0 means "not set". Gold customers can have individually negotiated prices (`customer_product_prices`, migration 087): saved ones apply automatically; admin/sales_director/ceo/operations_director can type a price per line in the order form (`price_override: true`) and it is remembered. Client `tierPrice`/`basePrice` in `orderCreate.js` only displays. Prices snapshot into the order at save time.
Customer tier FOLLOWS the Excel Customers-sheet `Tier` column (decided v1.245.0): every ERP sync sets `customers.customer_tier` for ERP-linked customers from `erp_tier` (bronze/silver/gold only; `competitor` customers and blank Tier cells are left alone; each change is logged in `customer_level_audit` as 'Tier from ERP workbook'). Manual tier edits on ERP-linked customers are therefore overwritten by the next sync.
TIN, legal name and legal address are auto-filled from the Customers-sheet `TIN`/`Legal Name`/`Address` columns (payload `tin`, `legal_name`, `legal_address`; the bot sends them for ALL customers in the top-level `customer_legal` list because Lily needs TINs for invoices -- customers[] is narrowed to debt/recent orders) ONLY where the app value is empty (typed/registry values stick); TIN must be 8 digits.
Warehouse inventory and Products page show the SILVER price by default as the "wholesale" price (`wholesale_price_amd` = silver, else bronze). The sync always refreshes tier prices and net cost from the workbook, even for manually edited products (name/brand/family/stock remain gated by `manually_edited_at`). Net cost comes from PriceList `Net Cost` (fallback Products `Net Cost AMD`).
Routes Distribution (region/subregion -> sales channel) now lives on the Route Plans page (`#/route-distribution`, `views/routeDistribution.js`): accordion tree with tri-state checkboxes, a channel button on every region/subregion row, bulk apply via `PUT /api/route-distribution/bulk`; editable by admin/sales_director/ceo/operations_director; the Settings admin row was removed.

## Orders
Workflow EXACTLY 5 stages: draft -> submitted -> confirmed -> packed_stock_out (one stage: "Packed / Stock Out") -> delivered. Orders for customers without ERP id stay `draft`. Discount (% or flat AMD, mutually exclusive) needs director approval (`approval_status`); changing a discount resets approval; editing items keeps it. Payment method `cash` | `invoice`. Brand name shown on warehouse staging/pick lists. Excel per-product discounts/price adds are shown as an extra row under the discounted line. Products are only ever real catalog products.
Accounting (Lily): after confirm, management sees a sheet to request a Բեռնագիր (waybill) for cash orders or Հաշիվ ապրանքագիր (invoice) for invoice orders; they can change the payment method on the same sheet; doc type always follows payment method. Lily guesses missing hc_codes (but hc_code is also synced from the workbook).
Delivery: driver/sales director/accountant/ceo/admin may move packed -> delivered without a route (drivers don't use the app). Sales director has warehouse-manager permissions.

## Location detection (v1.263.0)
- `getCurrentPosition` (util.js) is NOT a single high-accuracy/maximumAge:0 call (cold GPS fix = 20-60 s indoors, often fails). It reuses a fix <=15 s old (`rememberPosition`: map watch, 60 s broadcast, earlier screens), runs a fast coarse network fix AND a high-accuracy watch in parallel, resolves as soon as accuracy <= `goodAccuracy` (default 50 m) or after `refineMs` with the best fix, fails only at `timeout` with nothing (permission-denied fails at once). Errors show `locationErrorHint` (denied vs no signal). Map "my location" watch no longer switches itself off on TIMEOUT/UNAVAILABLE (only on permission denied) and pre-shows the last known fix. Check-in uses goodAccuracy 30 m / 25 s.

## Debt-collection tasks and quiet hours (2026-10-10, server-only)
- **When is a debt "overdue" (2026-10-10, `server/src/debtAge.js`)**: measured from the OLDEST UNPAID INVOICE, not from the last payment. Excel orders (`erp_order_lines`, grouped per order) are walked newest-first until they add up to the current debt (payments settle the oldest invoices first); that order's date + the customer's credit term (default 45 days) must be in the past. If the order history does not cover the debt (opening balance / no lines) the old rule applies (days since last payment, never paid = overdue). Used by the debt task, the reorder task's "no credit term exceeded" check and the Visit-first card. The cruder rule created a task for customer 10365 (never paid, debt = one 11-day-old order). Open tasks that are no longer overdue are CANCELLED by the next run (done/"paid" only when the debt is gone).
- **Debt FIFO, due chips, opening balance (v1.304.0, `server/src/debtAge.js`)**: the Excel debt is the truth and payments clear the OLDEST invoices first, so what is still owed is the NEWEST orders (walk newest -> oldest until they add up to `erp_customer_data.debt_amd`; an order is unpaid for `min(total, debt - newer orders)`). `GET /customers/:id/erp-orders` and `GET /sales` rows carry `unpaid_amd` and `due_days` (= days since the order - the customer's `credit_term_days`, default 45: > 0 overdue, <= 0 due in N days); `GET /customers/:id` carries `erp_balance0_amd` (Excel Balance0 = opening balance of the paper era before May 2025, may be negative = paid in advance, shown read-only under the credit limit in Account settings) and `debt_summary` (`oldest_due_days`, `overdue_amd`, `opening_unpaid_amd`, `opening_due_days`). Client: `debtChip.js` (`dueChipHtml` red "Due: 71 days" / amber "Due in 12 days", `unpaidRowClass` red tint = overdue, amber tint = unpaid within term, partly paid orders also show "Unpaid: amount"); chip on the Outstanding debt tile (top right), customer Orders list (plus an "Opening balance" row) and Sales page cards. ## Automatic tasks close themselves from the ERP data (2026-10-15, customer 10167)
- Owner report: Vaghinak's "collect the debt" task for Martin stayed open although the customer paid by bank transfer (arrives only via the workbook). Causes found and fixed (server-only, `debtCollectionTasks.js`, `vaghinak/chasers.js`):
  1. The ERP sync REPLACES `erp_customer_data`; a customer fully paid with no recent orders DROPS OUT of the extract, and the close rule required a row -> never closed. Now: absent from a real extract (>= 20 customers) = paid up -> task `done`, outcome `paid`.
  2. A bank transfer that clears the overdue invoices while newer in-term ones remain used to turn the task into `cancelled`; now `done` (paid) when the workbook shows a payment since the task was created (`last_payment_date` or a positive `erp_cashflow_lines` row), `cancelled` only when nothing was paid.
  3. Same family: `reorder_followup` tasks closed only on an app order -> now also when ERP order lines appear after the task; the Vaghinak downpayment chase counted only app `payments` -> now `GREATEST(app payments, ERP cashflow)` since the order date (never summed, a rep-recorded payment and its later cashflow line are the same money).
- Rule of thumb: any "done?" check for an auto task must also look at the workbook data (debt, last payment date, cashflow lines, order lines), because bank transfers and accountant orders never pass through the app.

## Typing masks keep the caret (1.355.0, owner 2026-10-18: "I cannot type number 6 on customer 10166's phone")
- Cause found by driving the real field: the phone mask (`installPhoneMask`, util.js) re-assigned the value after EVERY keystroke, which throws the caret to the end; inside a full number the extra digit was cut off the end, and backspace over a space did nothing. Fixing a digit in a saved number therefore "swallowed" keys. The digit 6 itself was never special (code has no digit-specific path) -- if the owner reports it again, ask for the exact steps/device.
- Now: caret restored by digit count (`phoneCaretAfter`), a digit typed inside a full number overtypes the next one, backspace after a space removes the digit before it. `bindAmdInput` (57,000 style fields) got the same caret fix. Rule: any live-formatting input must restore the caret; test by typing in the MIDDLE, not only at the end (`phone-mask.spec.mjs`).
- **Number fields = ghost of the old value (1.356.0, owner 2026-10-18):** the old "select everything on tap" is gone. Tapping an amount/number field (`.amd-input`, `.oc-field`, `type=number`, `inputmode numeric/decimal`) EMPTIES it and shows the old number as a faint placeholder (`.ghost-active`); typing replaces it, leaving without typing restores it. The restore also runs on `pointerdown` elsewhere and on Enter, because iOS does not blur a field when a button is tapped (otherwise Save would read ""). No `input` event is fired for the clearing. Guard: `ghost-number.spec.mjs`. Local flakes seen: `payment-handoff` / `orders-fresh` fail only in parallel runs on the shared DB, pass alone.
